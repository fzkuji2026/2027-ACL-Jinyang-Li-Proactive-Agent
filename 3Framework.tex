\section{Event-Driven Proactive Memory}
\label{sec:framework}

Figure~\ref{fig:architecture} summarizes \system{}.
The three memory levels differ by temporal resolution and validation strength, but all are scoped to one entity and contain evidence rather than intervention labels.

\subsection{Source Memory: Bounded Source-Level Evidence}

Source Memory preserves recent events exactly as represented in the public benchmark stream, without semantic rewriting.
For current event $e_t$, let
\begin{equation}
S_t=\operatorname{Tail}_{99}\{e_i:i<t,\ \tau_t-\tau_i\leq72\text{ h}\}.
\label{eq:source_memory}
\end{equation}
The current event is supplied separately, so $e_t\cup S_t$ contains at most 100 events and every retained prior event satisfies the 72-hour boundary.
The intersection is important: a sparse stream cannot reach farther back merely to fill the capacity, and a dense stream cannot exceed the item bound.
Source Memory gives the decision model exact recent evidence and a bounded context cost, but it does not explicitly express multi-day structure.

In parallel, a temporary buffer collects all events from the open local day.
The buffer is used for memory construction rather than injected wholesale into every decision.
When the day closes, its contents are consolidated and then cleared before the next day begins.

\subsection{Working Memory: Validated Daily Trajectories}

At each completed-day boundary, a construction LLM converts the temporary buffer into a compact trajectory: ordered episodes, observable context, outcomes, and citations to source event identifiers.
The construction prompt prohibits cross-day generalization and intervention decisions.
Its purpose is semantic organization, not labeling.

A deterministic fact validator then checks the entity, time interval, citations, and observable claims of each episode against the cited source-level events.
The LLM output is structured: the validator recursively flattens the \texttt{observed}, \texttt{context-before}, and \texttt{outcome} fields into typed scalar facts; free-text summaries and inferred fields are never treated as evidence.
Writing $F(d)$ for the replayable facts in daily episode $d$ and $C(d)$ for its cited source events, acceptance requires
\begin{equation}
F(d)\subseteq\bigcup_{e\in C(d)}F(e),
\qquad C(d)\subset E^u_{\text{completed day}}.
\label{eq:daily_validation}
\end{equation}
Two fields are consistent only when their canonical scalar values agree and their field paths match exactly or by a schema-preserving suffix, while every cited event exists in the same completed-day interval.
Unsupported claims and cross-entity or out-of-range citations are rejected.
Only accepted daily trajectories enter Working Memory.
Working Memory holds the validated days accumulated in the current weekly cycle; it is therefore a compact temporal view rather than another copy of source-level events.

\subsection{Long-term Memory: Replay-Validated Trajectories}

After Working Memory covers a completed week, a second construction LLM proposes longer-horizon temporal trajectories from the accepted daily evidence.
A proposal states a recurring context, an expected temporal pattern, its supporting days, and traceable daily evidence.
The LLM proposes structure but does not activate a rule or recommend a Push.

Each proposal is replayed deterministically over history available before the next decision.
Replay counts independent supporting days, checks that the pattern occurs in its stated temporal context, and censors periods without sufficient observation rather than treating them as failures.
A proposal becomes Active with at least three supporting days, replay confidence of at least $0.5$, and lift of at least $1.0$ over its historical base rate.
Well-formed, evidence-linked proposals that do not yet pass this gate remain Candidate and are replayed again on later weekly windows; malformed, out-of-window, or source-unlinked proposals are filtered before storage.
Candidate trajectories are retained only for future evidence accumulation and are never exposed in a decision Evidence Card until activated.
Long-term Memory persistently stores Active replay-validated trajectories and retrieves only those whose trigger context, weekday, and expected temporal window match the current event.
Because activation occurs only after a completed week, long-term evidence cannot leak from the test event into its own support.

\subsection{Evidence Card and Final Decision}

The online context is assembled as
\begin{equation}
C_t=\big(e_t, S_t, W_t, L_t, Q_t\big),
\end{equation}
where $W_t$ contains available daily trajectories, $L_t$ contains at most three relevant Active long-term trajectories, and $Q_t$ records a deterministic semantic-episode identity and evidence phase.
Long-term candidates are ranked first by temporal relation (deviated, pending, then not started), then by replay confidence and distance to the expected window.
An Evidence Card presents these components in separate fields with citations and temporal scope; a persistent intervention log joins $Q_t$ with prior Pushes to determine whether the episode has already been covered.
This prevents the decision model from confusing a current observation with a summarized trajectory or treating an unsupported interpretation as a fact.

Source-only, Source+Working, and Full \system{} use the same decision prompt and output schema.
They differ only in whether $W_t$ and $L_t$ are visible.
The shared prompt implements Equation~\ref{eq:or_semantics}: it asks whether the current event itself \emph{or} validated prior trajectories provide a concrete, timely, feasible, and low-risk service opportunity.
After the LLM proposes a decision, the shared Episode Controller applies the episode policy: it suppresses a repeated Push with the same episode identity and service intent, while a changed signature, strengthened evidence phase, changed service, or new local day opens a new opportunity.
The controller cannot create a Push or infer a service opportunity, and the identical policy is held fixed across PA-Prompt, Source-only, Source+Working, and Full \system{}.
The controller-finalized decision is the output used for scoring.
After a valid output, the event is committed to the daily buffer and Source Memory according to Equation~\ref{eq:causal_update}.

The full order is therefore: read strictly prior memory, stage the current event, assemble the Evidence Card, decide, commit the event, and run any newly due daily or weekly maintenance.
Reference labels are joined only after the prediction for offline scoring.
