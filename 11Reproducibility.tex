\section{Memory Implementation Details}
\label{app:implementation}

This appendix expands the evidence lifecycle in Section~\ref{sec:framework}; the core acceptance conditions and causal interfaces remain in the main paper.

\subsection{Daily Buffer and Checkable Fields}
Daily construction uses an independent buffer that preserves all committed events of the open local day alongside the bounded Event Memory.
The buffer is cleared after that day is processed.
Each daily segment records a local interval, typed \texttt{observed}, \texttt{context-before}, and \texttt{outcome} fields, and supporting event identifiers.
These activity segments are distinct from service episodes used for intervention control.
Scalar values are canonicalized; field paths must agree exactly or through a schema-preserving suffix.
The validator also checks entity, interval, and citation consistency.
Accepted facts have matching source values and resolved same-entity citations.
Validation and replay operate on typed evidence; free text supplies accompanying descriptions.
Accepted segments form daily trajectories retained in the current construction cycle, even after their source events leave Event Memory.

\subsection{Construction Clock and Replay Boundaries}
A weekly cycle is a time-ordered block of seven completed daily-trajectory records for one entity; each record belongs to one block.
Cycles advance with available daily records, so a cycle may span more than seven calendar days.
Empty or unobservable records advance cycle completion while leaving fulfilled and violated replay counts unchanged.
After consolidation, the online daily-memory view starts a new cycle, while daily records remain available for audit.

A proposal specifies trigger context $g$, expected pattern $p$, a local-time window, optional weekday restrictions, and supporting daily identifiers.
It describes a conditional behavioral expectation.
Replay evaluates days satisfying the applicability conditions and assigns censored status to missing observations.
An observable day with a matching trigger is fulfilled if $p$ occurs at or after the trigger within the specified window; otherwise it is violated.
Each date contributes at most once.
The confidence denominator in Equation~\ref{eq:replay_gate} includes only fulfilled and violated days.
Confidence is zero when the eligible-day count is zero; lift is zero when the base rate is zero.
The base rate uses observable days under the same window and weekday restrictions, including both triggered and other observable days.

\subsection{Pattern Lifecycle}
\label{app:lifecycle}
Lifecycle status controls retrieval eligibility, separately from current occurrence and service-episode states.
After admission, fulfilled and violated observations update stored confidence through a smoothed support ratio combining replay counts and subsequent outcomes with one initial success and one initial failure.
Censored observations leave success and failure counts unchanged.
Two consecutive violations move an Active pattern to \emph{weakening}, which remains retrievable at lower priority; four move it to \emph{dormant}.
A fulfilled observation restores a weakening pattern to Active when updated confidence is at least $0.5$.
A dormant pattern returns only to Candidate and requires replay readmission.
The retrieval-eligible lifecycle states are Active and weakening.

\subsection{Current Occurrence Matching}
\label{app:matching}
A deterministic matcher checks trigger context, weekday restrictions, and expected windows using a 30-minute lead and grace interval.
Triggers may be current or previously recorded causal occurrences.
Each occurrence has one of five states: upcoming, pending, fulfilled, deviated, or censored.
Retrieval considers upcoming, pending, and deviated occurrences of lifecycle-eligible patterns.
These occurrences are ranked by state (deviated, pending, then upcoming), lifecycle priority, stored confidence, and temporal distance; at most three patterns enter $R_t$.
All matching and state assessment use only the current event and causally available observations.
Daily Trajectory Memory supplies all completed daily trajectories in the current cycle.

\subsection{Episode Identity and Causal Execution}
\label{app:episode_control}
In Sports/Home, the controller forms an intervention key from scope-specific episode state, proposed service action and target, and sorted pattern identifiers present in the decision context.
The identifier component contains the explicit pattern identifiers available in context and defaults to an empty list for plain summaries or graph facts.
State includes availability/activity context for Sports and activity/room context for Home.
Home additionally distinguishes onset, confirmed, and sustained phases at one, two, and three or more consecutive matching observations, respectively.
When an explicit episode key is unavailable, scope-specific time or target fields identify the opportunity, and unchanged evidence is additionally required for duplicate suppression.
Changed episode state, a restarted state sequence, changed service or pattern identifiers, or a new local day can produce a different intervention key; this permits the decision model to reassess service value.

In Code, matching uses repository-object identity and the most recent allowed intervention's mode, recipient, content, and firing condition.
An exact match suppresses a repeated \texttt{create} proposal by converting it to \textsc{Abstain}.
Changed signatures or other episode operations pass this duplicate check.
Re-entry follows these identity and phase rules, with each intervention originating from an LLM proposal.
All main-table methods and memory-level variants share this policy; each method's available evidence determines its proposal's identity.

The causal execution order is:
\begin{enumerate}
\item Prepare prior memory; any due maintenance uses only previously committed events.
\item Stage $e_t$ as the current input, defer its memory commit until the decision is finalized, and select daily and temporal evidence.
\item Obtain the decision LLM's proposal from the structured context.
\item Apply repeated-opportunity suppression and finalize the output.
\item Commit $e_t$ and update coverage state; maintenance incorporating $e_t$ affects only later decisions.
\end{enumerate}
Reference labels are joined only for offline scoring.

\section{Public Events and Reference-Label Protocol}
\label{app:benchmark_protocol}

\subsection{Scopes and Public Events}

\paragraph{Sports.}
This scope derives from HeartSteps mobile activity contexts~\citep{klasnja2019heartsteps}.
We retain 1,456 meta-events from nine complete participant streams, covering 367 observed participant-days.
Complete participant streams preserve the chronology required for daily and longer-term memory construction.
Public fields include decision-time availability, recognized activity, recent step summaries, location category, weather, and local decision slot.
Randomized treatment assignments and future behavioral outcomes are excluded.
Reference labels concern opportunities for optional activity support.

\paragraph{Home.}
This scope derives from CASAS ambient-sensor traces~\citep{cook2013casas} and contains four homes with 14 consecutive days each.
Within every local day, ten-minute preprocessing blocks are merged into 28 regular 50-minute segments and one 40-minute tail, producing 406 events per home.
Every source block is assigned to exactly one segment, preserving the complete two-week chronology.
A segment becomes available only after its interval closes and contains within-interval motion counts, room sequences, door actions, and compact numeric summaries.
Each public segment describes its own interval; the evaluated agent derives historical evidence from preceding same-home observations.
The service space is restricted to gentle, low-risk check-ins and excludes disease, fall, travel, danger, and unsupported preference inference.

\paragraph{Code.}
This scope organizes 1,459 repository activity records into four isolated streams, with 174 reference interventions (Table~\ref{tab:benchmark_stats}).
Each event represents a timestamped repository activity, such as a commit push, issue update, pull-request action, or review.
We preserve GitHub's native event granularity, with each event corresponding to one intervention decision.
Within each repository, records are ordered by event time, with event ID used to break ties deterministically.
The source inventory includes public GH Archive records~\citep{gharchive}.
Each repository independently maintains Event Memory, Daily Trajectory Memory, and Temporal Pattern Memory, together with its intervention history and episode state.
Observations, extracted evidence, and coverage state remain local to each repository, including projects with shared contributors.
The repository stream is the memory owner and evaluation unit.
Services include low-risk triage, review, and maintenance assistance.
Native \texttt{PushEvent} denotes repository activity; \textsc{Intervene} denotes an agent's service decision.

\paragraph{Public-input contract.}
Reference-positive and reference-negative events follow the same scope-specific public schema.
Public inputs contain only event identifiers, stream identifiers, timestamps, and contemporaneously observable fields. Reference labels, candidate flags, episode annotations, memory-level markers, and scoring masks remain evaluator-private; agents construct trajectory summaries and memory representations from public observations.
The inventory includes early events observed before Daily Trajectory Memory or Temporal Pattern Memory becomes available.

\subsection{Reference Labels and Causal Replay}
\label{app:reference_protocol}

\paragraph{Service-opportunity semantics.}
Annotators assess the current event $e_t$ and the complete strictly prior public history $\mathcal{H}_{<t}=(e_1,\ldots,e_{t-1})$ of the same entity, independently of the memory representation retained by a tested method.
Let $A(e_t)$ indicate that the current event itself establishes a concrete, timely, feasible, and low-risk service opportunity, and let $B(e_t,\mathcal{H}_{<t})$ indicate that prior evidence makes such an opportunity visible at the current event.
Let $N_t^{\mathrm{ref}}$ indicate opportunity novelty under the reference episode protocol below.
The reviewed label follows Equation~\ref{eq:or_semantics}.
These predicates specify annotation semantics.
Annotators assess concrete service value in both routine and unusual situations, using current observations and prior evidence.
Within a semantic episode, the first reliable and actionable window is labeled \textsc{Intervene}.
Subsequent covered windows are labeled \textsc{Abstain} unless the evidence strengthens, the feasible service changes, or the episode reopens.
Reference episode coverage, and hence $N_t^{\mathrm{ref}}$, is determined from the reviewed opportunity sequence up to the current event, independently of a method's predicted interventions.
The labels represent reviewed service opportunities.

\paragraph{Annotation protocol.}
An LLM-assisted screening stage identifies potential service opportunities and expands the review queue.
Three team members then independently assign initial labels while blinded to the evaluated systems' decisions, followed by team cross-review and adjudication.
Every public event enters final review, covering the full inventory beyond the screening shortlist.
The screening output prioritizes inspection; team adjudication determines each reference label.
We use protocol-fixed evaluation on the jointly developed benchmark; independent held-out testing remains future work.
The Home aggregation rule is specified before its event rows are constructed, and each evaluation version jointly records its event inventory, reference-label map, intervention prompt, Event Memory boundary, and validation settings.
For the main comparisons, these labels, prompts, memory bounds, and validation settings are frozen before the corresponding runs.

\paragraph{Causal replay.}
Every participant, home, or repository stream is replayed independently from empty method state and in timestamp order.
At event $t$, a method may access the current event $e_t$, its own strictly prior same-stream memory, and any preceding outputs retained by its architecture.
Access is restricted to the current public event and causally available same-stream state.
The intervention decision is finalized before $e_t$ is committed to memory.
Daily and weekly maintenance involving $e_t$ can therefore affect only later decisions.
Reference labels remain evaluator-private during inference and are joined afterward for scoring.
Annotation artifacts, reference episode states, and scoring metadata remain organizer-private.

\section{Additional Experimental Configuration}
\label{app:configuration}

\paragraph{External baselines.}
\emph{ProactiveAgent} adapts ProactiveAgent's released evaluation prompt and proposal/null output contract~\citep{lu2025proactiveagent,thunlp2026proactiveagentrepo}, using the study backbone.
It retains causal event--decision history, capped at 1,000 events including the current event per request, as its memory interface.
\emph{Mem0} uses the open-source \texttt{mem0ai==2.0.12} extraction, consolidation, and retrieval pipeline~\citep{chhikara2025mem0,mem0ai2026mem0v2012}, local \texttt{all-MiniLM-L6-v2} embeddings, top-$8$ same-entity retrieval, and a $0.1$ search threshold.
The baselines retain their method-specific memory and prompt interfaces while sharing the task semantics and final Episode Controller.
Each method retains its configured context and token budgets.

\emph{A-MEM} uses linked memory notes and association updates~\citep{xu2025amem}; retrieved notes augment the bounded event context.
\emph{ContextAgent} uses the in-context proactive-service formulation of ContextAgent~\citep{yang2025contextagent}, adapted to the public event representation and study backbone.
These event-stream adaptations are evaluated on the same scope-specific reference labels as the other main-table methods.

\paragraph{Cross-week summary control.}
CSM is the in-house recursive-summary control evaluated in Section~\ref{sec:recursive_summary}.
It summarizes each completed local day and, after seven completed observed daily records, combines that block with the previous cross-week summary.
The block follows observed dates and may span more than seven calendar days.
This recursive update combines retained information from earlier weeks with the latest block.
The decision context contains the current event, bounded Event Memory, completed daily summaries in the current block, and the latest cross-week summary.
The adapter caps daily and cross-week summaries at 2,000 and 6,000 characters, respectively.
CSM checks output format and length before supplying the summary text directly to the decision model.
Its construction inputs contain only committed public observations; prior decisions are recorded separately for controller state and resumption.
Daily and cross-week versions retain source links for auditing, while the decision model interprets the summary prose for current service value.

\paragraph{Temporal-graph baseline.}
Graphiti uses the open-source temporal-graph framework~\citep{zep2026graphiti} to ingest committed public events into a stream-isolated graph.
The adapter uses Graphiti 0.30.2, Neo4j, and local 384-dimensional \texttt{all-MiniLM-L6-v2} embeddings.
The current public event is the retrieval query; native hybrid edge search with reciprocal-rank fusion returns at most ten relation facts, including validity fields and source-record identifiers.
The adapter supplies the retrieved relation facts and their source identifiers directly.
Graphiti's ingestion episodes denote source records; evaluation episodes denote service opportunities.
CSM and Graphiti retain ProactMem's 72-hour/100-event bound for the event context and reuse the task policy, output contract, and Episode Controller with memory-specific guidance.
CSM supplies summary text and Graphiti supplies relation facts through their respective memory interfaces.
The comparison evaluates alternative memory interfaces with method-specific prompt guidance and computational budgets.

\paragraph{Memory-level variants.}
\emph{Event-only} receives the current event and bounded Event Memory (Equation~\ref{eq:source_memory}).
\emph{Event+Daily} additionally receives fact-validated daily trajectories; \system{} also receives eligible temporal patterns (Equation~\ref{eq:long_term_retrieval}).
These three variants share the intervention prompt, output schema, and Episode Controller, differing in available memory evidence.

\paragraph{Mechanism ablations and controller diagnostic.}
Section~\ref{sec:validation_ablations} defines two evidence-check ablations and a suppression diagnostic; Table~\ref{tab:validation_ablations_full} reports their intervention rates, Relevance, Coverage, and Effectiveness.
Each validation ablation removes only its named check.
The controller diagnostic compares recorded proposals with finalized outputs on the same Code sequence, holding later states and decisions fixed.

\paragraph{Model roles and implementation.}
In the primary setting, decision and memory-construction calls use \texttt{gpt-5.6-luna} through the official OpenAI API, with temperature zero and thinking disabled.
Decision generation and memory construction have separate call roles and output budgets.
Decision limits are interface-specific (256 or 512 tokens); construction-call limits are configured separately and recorded by role in the run configuration.
Event Memory contains at most 99 prior events within 72 hours, plus the separately supplied current event.
Daily construction follows local-day closure; weekly construction and replay follow seven completed daily records as defined in Section~\ref{sec:framework}.
All memory and validation records are entity-scoped.

We also test \texttt{gpt-5.6-terra} and \texttt{gpt-5.6-sol}.
Both decision and construction LLMs change together; Section~\ref{sec:model_sensitivity} provides the fixed settings and complete results.
Input manifests, prompts, schemas, thresholds, and role-specific configurations are versioned in the experiment ledger.

\paragraph{Scoring.}
Section~\ref{sec:experimental_settings} defines the scoring policy and metrics.
Using event-level confusion counts, Relevance is $\mathrm{TP}/(\mathrm{TP}+\mathrm{FP})$, Coverage is $\mathrm{TP}/(\mathrm{TP}+\mathrm{FN})$, Effectiveness is $2\mathrm{TP}/(2\mathrm{TP}+\mathrm{FP}+\mathrm{FN})$, and Balance is $\tfrac{1}{2}[\mathrm{TP}/(\mathrm{TP}+\mathrm{FN})+\mathrm{TN}/(\mathrm{TN}+\mathrm{FP})]$.
Effectiveness is the harmonic mean of Relevance and Coverage; the reported percentages use the same reference labels and finalized decisions as the other event-level metrics.
Intervention Rate measures decision frequency.

\subsection{Intervention-Rate Interpretation}
\label{app:rate_interpretation}
Writing $\rho$ for reference-positive prevalence, the count decomposition is
\begin{equation}
\mathrm{IR}=\rho\,\mathrm{Coverage}+(1-\rho)\,\mathrm{FPR}.
\label{eq:intervention_frequency}
\end{equation}
All quantities are fractions; the terms count recovered opportunities and false interventions.
The prevalences are 25.1\%, 11.7\%, and 11.9\% in Sports, Home, and Code.
